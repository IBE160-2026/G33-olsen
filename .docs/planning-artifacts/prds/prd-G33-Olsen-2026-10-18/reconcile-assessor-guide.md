# PRD Reconciliation with the Assessor Guide

## Purpose

This note reconciles the ProsjektMelk PRD with the IBE160 assessor guide for Part 1. It does not add product scope. It separates requirements that should guide later planning and implementation from evidence that can only be produced during delivery.

The PRD is already strong on the product core: deterministic MRP, complete keyless operation, input validation, persistence and reset, supplier follow-up, staged scope, accessibility principles, and clean-start runability. The main gaps are not additional features; they are explicit assessment evidence and acceptance criteria around how the product is built, verified, and handed over.

## Reconciliation by assessment area

| Assessment area | Current PRD coverage | Gap to carry into downstream plans | Evidence required at delivery (not satisfiable by the PRD alone) |
|---|---|---|---|
| **Process and AI governance (30%)** | The purpose, NFR-9, release gates, and documentation-drift risk require traceability, prompts, reviews, tests, corrections, and small descriptive commits. | Define a lightweight traceability convention from `FR/NFR -> epic/story -> implementation -> test -> commit`. Define where prompts or AI-session summaries, decisions, review findings, corrections, and approved deviations are recorded. Branches, issues, or pull requests may support the workflow, but should only be required if the team actually uses them. | A credible history over time; small descriptive commits; maintained planning artifacts; saved prompt/session evidence tied to concrete changes; examples where AI output was challenged or corrected; decision records with rationale; explained departures from the approved proposal or PRD. These records must be created as work happens, not reconstructed at the end. |
| **Functionality and scope (20%)** | FR-1 through FR-24 define coherent end-to-end flows, failure behavior, non-trivial calculation rules, persistence, supplier history, and optional AI. Release increments protect the core. | Add a proposal-to-PRD scope reconciliation before stories are finalized, so every promised feature is implemented or explicitly deferred with a reason. Give each core journey end-to-end acceptance criteria, including repeated actions, restart persistence, reset, invalid input, and no-key operation. Keep cups, lids, foil seals, and yogurt/raw ingredients present in the coherent baseline. | A running app that completes the README’s core journeys; stable behavior under invalid input and repeated use; screenshots or a short demo as supporting evidence only; a final scope/deviation note matching the delivered app. Passing documents cannot substitute for working functionality. |
| **Quality assurance and testing (15%)** | NFR-1, NFR-3, NFR-8, SM-1, SM-3, and SM-5 demand automated scenario, validation, flow, persistence, reset, statistics, and fallback verification. | Turn these into a test strategy with named unit, integration, and end-to-end responsibilities. | **Design and user experience (10%)** | UJ-1 through UJ-4, NFR-5, NFR-6, and SM-2 cover understandable states, English language, labels, keyboard access, contrast, responsive behavior, and a comprehension check. | Produce a small UX specification or wireframe covering navigation, hierarchy, calculation disclosure, alerts, empty/loading/error/success states, reset confirmation, supplier comparison, and narrow-width behavior. Make accessibility acceptance explicit for semantic controls, focus visibility/order, form errors, non-color status cues, readable contrast, and alternative text for meaningful images. | Dated sketches or UX decisions; completed keyboard and responsive checks; accessibility findings and fixes; and the documented usability check from SM-2. The assessor will judge the actual interface, so design documentation alone is insufficient. |
| **Code quality and architecture (10%)** | NFR-7 separates calculation, persistence, presentation, and provider responsibilities; the constraints preserve deterministic core behavior and server-only secrets. | Create an architecture document before implementation that maps modules, state and data flow, persistence ownership, API/provider boundary, configuration, error handling, and dependency direction. Record technology choices and trade-offs. | **README and runability (10%)** | NFR-2 and SM-3 require a clean-start rehearsal without login, API key, paid access, or private infrastructure. | Treat README content as an acceptance requirement: product/user summary; screenshot; supported runtime and exact version; copyable install/start/build commands; optional environment variables and `.env.example`; explicit no-key behavior; demo data and reset instructions; core scenario walkthrough; test/lint/format commands; relevant folder overview; and links to planning/process artifacts. If any secret was ever committed, it must be revoked and removed appropriately—deleting only the current file is insufficient. |

## Highest-priority follow-through

1. Keep implementation narrow and prove increments 1 and 2 before the optional provider increment; the assessor rewards a complete, stable core more than extra breadth.
2. Establish traceability and evidence conventions before coding begins. Process evidence is 30% and cannot be credibly recreated at submission time.
3. Convert the scenario and failure requirements into executable tests and README commands as each story is completed, then record review findings and AI-generated defects that were corrected.
4. Create the architecture and UX artifacts before their corresponding implementation, and update them whenever the implementation intentionally diverges.
5. Finish with a clean-clone assessor rehearsal and repository audit. Record the environment, commands, results, and any correction made during the rehearsal.

## Interpretation rule

The PRD should describe what the product and delivery process must achieve. Commits, prompts, reviews, test reports, usability notes, screenshots, clean-clone logs, and repository audits are later evidence that those requirements were actually met. Their absence cannot be repaired merely by adding claims to the PRD.
